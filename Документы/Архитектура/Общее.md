# Архитектура онлайн-платформы с курсами

Этот документ описывает высокоуровневую архитектуру для образовательной онлайн-платформы, спроектированную для гибкости, масштабируемости и интеграции с AI-сервисами.

## 1. Фронтенд: Гибридная модель (Микрофронтенды)

Используется гибридный подход, где приложение-оболочка (Shell) на Next.js хостит в себе интерактивные модули (Remotes) на Vite.

### Основное приложение (Host/Shell)
*   **Технология:** **Next.js**
*   **Ответственность:**
    *   Все публичные страницы с высоким требованием к SEO (главная, описания курсов, страницы лекций).
    *   Общий каркас сайта: Header, Footer, навигация.
    *   Серверный рендеринг (SSR/SSG) для быстрой загрузки и индексации.
    *   Маршрутизация, включая локализацию (`/ru/`, `/en/`).

### Интерактивные модули (Remotes)
*   **Технология:** **React + Vite**
*   **Ответственность:**
    *   Сложные, state-heavy компоненты, где SEO не критично.
    *   Примеры: решатель задач, интерактивный граф карты курсов, личный кабинет.

### Метод интеграции
*   **Технология:** **Module Federation**
*   **Процесс:** Next.js-приложение динамически (`dynamic import` с `ssr: false`) подгружает бандлы Vite-приложений как компоненты, обеспечивая бесшовный пользовательский опыт в рамках одного домена.

## 2. Бэкенд: Сервис-ориентированный подход

### Core API
*   **Технология:** **Express.js (Node.js)**
*   **Роль:** Основной BFF (Backend for Frontend), мозг приложения.
*   **Задачи:**
    *   Предоставление REST API для всех фронтенд-частей.
    *   Бизнес-логика: управление пользователями, прогрессом, сущностями.
    *   Аутентификация (выдача JWT в `HttpOnly` cookie).
    *   Постановка тяжелых задач в очередь.

### Асинхронные задачи
*   **Технология:** **Redis + BullMQ**
*   **Роль:** Система очередей для обработки длительных и ресурсоемких операций без блокировки основного API.
*   **Примеры задач:** AI-ревью кода, генерация отчетов, массовые рассылки.

### Воркеры (Workers)
*   **Технология:** Отдельные **Node.js** процессы.
*   **Роль:** Исполнители, которые слушают очередь, забирают задачи и выполняют их. Например, `CodeReviewWorker` общается с GitHub API и OpenAI API.

## 3. База данных и хранение

### Основная СУБД
*   **Технология:** **MongoDB**
*   **Причина:** Гибкость для хранения сложных, вложенных структур данных (графы, версионирование).
*   **Структура сущностей:**
    *   **Карты:** Документы с массивами `nodes` (узлы) и `edges` (ребра), реализующие граф.
    *   **Лекции и Задачи:**
        *   **Версионирование:** Реализовано через массив `versions` внутри одного документа.
        *   **Локализация:** Вложенные объекты для разных языков (например, `title: { ru: "...", en: "..." }`).
        *   **AI-контент:** Текст лекций разбит на массив чанков `content_chunks`, где каждый чанк содержит текст и его векторное представление (`embedding_vector`).

### Векторный поиск
*   **Технология:** **MongoDB Atlas Vector Search**
*   **Роль:** Обеспечивает мгновенный семантический поиск по смыслу, а не по ключевым словам. Используется для AI-чата и глобального поиска.

## 4. Интеграция с AI

### Создание векторов (Embeddings)
*   **Стартовый вариант (Рекомендуемый):** Через API **OpenAI** (модель `text-embedding-3-small`). Просто, быстро, качественно.
*   **Продвинутый вариант (На будущее):** Запуск собственной Open Source модели с **Hugging Face** на своем сервере для экономии и полного контроля данных.

### AI-чат по лекциям
*   **Метод:** **RAG (Retrieval-Augmented Generation)**.
*   **Процесс:** Вопрос пользователя → Векторизация → Поиск релевантных чанков текста в MongoDB → Отправка найденных чанков + вопроса в LLM (GPT) для генерации точного ответа.

### AI-ревью кода
*   **Доступ:** Через создание **GitHub App**, которое пользователь устанавливает на свой репозиторий.
*   **Процесс:** Асинхронно через очередь. Воркер получает `diff` Pull Request, в цикле анализирует каждый измененный файл, отправляя в LLM только его изменения, и публикует комментарии к конкретным строкам кода через GitHub API.

## 5. Общая схема взаимодействия (Пример)

1.  **Пользователь** заходит на страницу с картой курса.
2.  **Next.js** (сервер) запрашивает данные у **Express API**.
3.  **Express API** получает данные из **MongoDB** и отдает их.
4.  **Next.js** рендерит страницу с общим каркасом.
5.  **На клиенте** `Module Federation` подгружает **Vite-приложение** (интерактивную карту).
6.  **Пользователь** отправляет задачу на ревью.
7.  **Express API** принимает запрос, ставит задачу в **очередь Redis** и мгновенно отвечает `202 Accepted`.
8.  **Воркер** забирает задачу, обрабатывает ее (обращаясь к GitHub и OpenAI).
9.  **Воркер** сохраняет результат ревью в **MongoDB**.
10. **Фронтенд** (через WebSocket или пуллинг) получает уведомление о завершении и отображает результат пользователю.
